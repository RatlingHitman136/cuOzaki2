# ozaki

Learning project: emulate FP32 / FP64 / double-double (dd) GEMM on GPU integer tensor cores
(int8, later int4) using the Ozaki scheme. C++20 + CUDA + CCCL (Thrust, CUB, libcu++).

## Focus

**Ozaki scheme II only** (integer/modular: A, B -> integer matrices, N small-modulus int8 GEMMs,
CRT reconstruction). Start with a CPU implementation in `src/ozaki_cpu.cpp`, validated against a
long-double GEMM (kept inside the tests), then port step by step to CUDA. Scheme I (slicing) is out of scope.

## Goal

Compute `C = A * B` in (near) higher precision by:

1. **Slicing**: split each FP matrix into several low-bit integer slices with a per-row (A) /
   per-column (B) power-of-two scale, so slice products are exact in the integer accumulator.
2. **Integer GEMMs**: multiply slice pairs on tensor cores (int8 x int8 -> int32, exact).
3. **Accumulation**: scale and sum the partial products in FP32/FP64/dd, error-free where possible.

Then measure: accuracy vs. a reference, and throughput vs. cuBLAS SGEMM/DGEMM on this GPU.
The number of slices is the accuracy/speed knob.

Milestones (in order; do not skip ahead):

1. Toolchain smoke test (done when `ctest` passes).
2. Reference CPU GEMM in higher precision (long double / dd) for ground truth.
3. Slicing + reconstruction on host; verify `sum(slices) == original` to the target precision.
4. Naive int8 GEMM kernel, then `mma.sync` / WMMA int8 version.
5. End-to-end FP32 emulation; error vs. slice count; benchmark against cuBLAS.
6. FP64 and dd emulation.
7. int4 variant (check what sm_89 actually supports before designing around it).
8. Optimise (tiling, shared memory, pipelining, fused accumulation).

## Hardware / toolchain

- GPU: RTX 4070 SUPER, compute capability 8.9 (Ada), under WSL2. FP64 is heavily throttled on
  consumer GPUs, which is exactly why emulation is interesting here.
- CUDA toolkit 13.x at `/usr/local/cuda` (CCCL comes bundled via `CUDA::cccl`).
- CMake >= 3.31, C++20, Unix Makefiles (ninja not installed).

Build:

```
cmake --preset release
cmake --build --preset release -j
ctest --preset release
```

If the CUDA 13 host-compiler check fails with the default `g++`, install/pin an older one via
`-DCMAKE_CUDA_HOST_COMPILER=g++-13`.

## Layout

```
include/ozaki/   public headers: ozaki_cpu.hpp (CPU pipeline, one function per step),
                 ozaki.hpp (CUDA helpers)
src/             ozaki_cpu.cpp (pure C++ library `ozaki_cpu`), ozaki.cu (CUDA library)
tests/           correctness tests (ctest), one executable per topic
bench/           benchmarks vs. cuBLAS
```

## Guidelines

- **This is a learning project. The user writes the kernels.** Explain concepts and review; do
  not hand over finished kernels unless asked. Small hints and skeletons are fine.
- Explain each step taken; prefer small, understandable increments over big changes.
- Never run `git commit` / `git push`; leave version control to the user.
- Do not add tool attribution, "generated by" notes, or AI mentions to source files, comments,
  commit messages, or docs.
- Modern C++: C++20, RAII, `std::span`, `constexpr`, `<cstdint>` fixed-width types; no raw
  `new`/`delete`; avoid macros except the CUDA error-check one. Prefer CCCL (CUB/Thrust/libcu++)
  over hand-rolled equivalents unless the point is to learn the hand-rolled version.
- Every CUDA call is error-checked (`CUDA_CHECK`); check kernel launches too.
- Correctness before speed: each kernel gets a test against a trusted reference first.
- Benchmark in Release only; warm up, use CUDA events, report TFLOP/s (or TOP/s for int8).
- Errors are measured in ulps / relative error against a higher-precision reference, not
  eyeballed.
- Comments explain *why* (numerical reasoning, invariants), not what the code says.
